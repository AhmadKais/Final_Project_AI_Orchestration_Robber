# Sample Reports

The four mandatory JSON report types (Sec. 9.3.3, Appendix F Table 20), generated from an **actual played match** -- not fabricated data. Regenerate anytime with:

```bash
uv run python scripts/generate_sample_reports.py
```

| File | Role (Table 20) |
|---|---|
| `declaration_demo-001.json` | `[Declaration File]` — team/repo/MCP-address/hardware identities, fixed for the whole game. Hardware comes straight from the real Step-0 exchange each `Orchestrator` runs at the start of `run_game()` (Sec. 5.5) |
| `config_demo-001_g01.json` | `[Configuration File]` — the actual `config/game.json` this match ran under |
| `log_demo-001_g01.json` | `[Log File]` — every Commit-Reveal step from both sides; `ReplayViewer(...).verify_all()` returns `True` on it |
| `result_demo-001.json` | `[Results File]` — the real outcome and score from this match |

These are illustrative examples for understanding the format (same purpose as the four sample files the spec itself attaches to the book) -- not real league submissions. Real per-match artifacts belong in the gitignored `logs/`/`reports/` directories instead, generated by `simulation_sdk.run_peer` during actual play.

**See also**: [`series/`](series/) — the same four artifact types for a full **6-game league series** (Appendix F Table 18), generated by `simulation_sdk.run_peer_series`/`SeriesRunner` instead of a single game.
